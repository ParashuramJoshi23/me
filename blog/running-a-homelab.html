Running a Homelab

June 2026 · ~7 min read

For a few years now I've kept a small pile of computers humming away in a corner of my apartment. It started as a single mini PC running one service and has slowly grown into a proper little homelab — the place where I host my own tools, break things on purpose, and learn how the infrastructure I use at work actually behaves when I'm the one holding the pager.

This post is a tour of why I bother, what's in the rack, and the lessons that only show up after something has been running (and occasionally falling over) for a while.

Why run a homelab at all?

The honest answer is that it's the best way I've found to learn. Reading about networking, storage, and orchestration only gets you so far; wiring it up yourself and living with the consequences teaches a different, stickier kind of knowledge. A few reasons it's been worth it:

  • A real environment to experiment in. I can try a new database, a service mesh, or a backup strategy without a cloud bill ticking in the background or a production incident on the line.
  • Owning my own data. A handful of the SaaS tools I used to pay for now run on hardware I control, on my network.
  • Empathy for ops. Once you've been woken up by your own flaky disk, you write very different runbooks at work.
  • It's genuinely fun. There's a quiet satisfaction in a dashboard full of green.

The hardware

I'm a big believer in starting small and cheap. You do not need a 42U rack to call it a homelab — a single second-hand machine is a fine beginning. My current setup is deliberately modest and power-efficient:

  • A small compute node — a mini PC with a low-power CPU and 32 GB of RAM. This does most of the heavy lifting and idles quietly.
  • A NAS for storage — a few disks in a mirrored pool for the things I actually care about keeping.
  • A Raspberry Pi for the always-on, low-power jobs that shouldn't share fate with the main box (DNS, monitoring).
  • A UPS — the unglamorous purchase I should have made first. Clean shutdowns during power cuts are worth every rupee.
Lesson learned early: buy the UPS and the extra disk before you buy the third compute node. Reliability beats horsepower in a homelab.

The software stack

The hardware is the boring part — the fun is in what runs on it. Everything is containerized so I can move it between machines and rebuild from scratch when (not if) something goes wrong.

  • OS: a stable Linux base on each node, kept boring on purpose.
  • Containers: Docker Compose for most services, defined as code in a Git repo so the whole thing is reproducible.
  • Reverse proxy: a single ingress that handles TLS and routes service.home.example hostnames to the right container.
  • DNS & ad-blocking: a local resolver so everything on the network gets clean DNS and internal names.
  • Monitoring: metrics, dashboards, and alerts so the lab tells me when it's unhappy instead of me finding out the hard way.

A representative slice of a compose file looks like this — nothing exotic, just declarative and version-controlled: 

services:
  proxy:
    image: caddy:latest
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - caddy_data:/data

volumes:
  caddy_data:

Networking

Networking is where a homelab starts to feel real. A few things that made a big difference:

  • A separate VLAN for lab gear, kept away from the phones and TVs on the main network.
  • Static leases for anything that hosts a service, so addresses don't shuffle around and break my proxy config.
  • A VPN back in (I use a WireGuard-based mesh) so I can reach the lab from anywhere without exposing it to the open internet.

That last point matters: my default is that nothing is exposed publicly. If I need remote access, it goes through the VPN. Fewer open ports, fewer 3 a.m. surprises.

Backups, or: how I learned to relax

The first rule of a homelab is that the lab will break. Disks die, upgrades go sideways, and one day you'll rm -rf the wrong directory. Backups are what turn a disaster into an inconvenience.

I keep to a simple version of the 3-2-1 rule:

  • 3 copies of anything important,
  • 2 different kinds of media,
  • 1 copy off-site (encrypted, in cheap cloud storage).

Just as important: I actually test restores. A backup you've never restored from is a hope, not a backup.

Lessons learned

  • Start small. One machine, one service. Grow it as you hit real limits, not imagined ones.
  • Treat config as code. If you can't rebuild a service from a Git repo, you don't really own it — the machine does.
  • Boring is a feature. Stable base images and well-trodden tools beat the shiny new thing when it's 11 p.m. and something is down.
  • Monitor before you scale. You can't fix what you can't see.
  • Document as you go. Future-you will not remember why that one container needs that one weird flag.

Where it's headed

The lab is never really finished, which is part of the appeal. Next on my list is tightening up automated provisioning so a dead node can be replaced in minutes, and getting alerting quiet enough that it only pages me when it truly matters.

If you've been thinking about starting one: get a cheap second-hand machine, pick one service you wish you self-hosted, and go. The rest follows.
